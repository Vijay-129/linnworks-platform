# Coding Conventions

Rules code generated against this platform should follow. Derived from the actual
patterns already established across `LinnworksAPI/` (~1,200 files, v1 ported +
v2 written fresh) — these are observed conventions, not invented ones. Checked by
the MCP server's `check_against_standards` tool.

This file covers the SDK layer. For macro-authoring conventions (structure,
logging, rate-limit handling, idempotency), see `macro_conventions.md` — those
rules are derived from real approved macros in `golden_examples/`, not guessed at.

## Naming

- Classes/interfaces/enums/methods/properties: PascalCase. Interfaces prefixed `I`
  (`IOrdersController`, `IProxyFactory`).
- Method parameters and local variables: camelCase.
- One type per file, filename matches the type name exactly (`StockLocation.cs`
  contains `class StockLocation`). This is what makes the `port_controller.py` /
  `generate_v2_models.py` tooling able to resolve dependencies mechanically — don't
  break it by putting multiple types in one file or renaming a file without renaming
  the type.
- Known exception, not a pattern to copy: `ClassBase/batchAssignment.cs` in the
  legacy source has a lowercase-leading class name. It was ported as-is
  (`LinnworksAPI/V1/Controllers/Orders/Models/batchAssignment.cs`) to match the
  real wire behavior — don't "fix" the casing, that would break JSON round-tripping
  against however the actual API serializes it.

## Models

- Every v1 model class inherits `LinnObject` (a marker base, currently empty —
  see `LinnworksAPI/Core/LinnObject.cs`). v2 models do not (different namespace,
  no shared base needed since v2 has its own generator).
- Optional value-type fields are `Type?` (`Guid?`, `Int32?`, `DateTime?`,
  `Boolean?`). Optional reference-type fields (`String`, `List<T>`) are just the
  bare type — this project targets C# 7.3/netstandard2.0, which has no nullable
  reference type annotations, so `String?` is a compile error, not a style choice.
- Enums use `[JsonConverter(typeof(StringEnumConverter))]` so they serialize as
  their string name, not an integer, matching how Linnworks' API represents them.

## Error handling

- v1 (`LinnworksAPI/Core/Factory.cs`): any non-2xx response is deserialized as
  `{Message: string}` and re-thrown as a plain `Exception` carrying that message.
  There is no retry, backoff, or rate-limit-aware handling built in — a caller
  that needs resilience has to add it at the call site, not assume the SDK does it.
- v2 (`LinnworksAPI/V2/Core/RestClient.cs`): same idea, but the thrown `Exception`
  includes the HTTP status code and raw response body (`"v2 API error {code}: {body}"`),
  since v2 errors are JSON problem-details, not a single message string.
- Don't swallow exceptions in generated code. If a macro needs to continue past a
  failed call, catch explicitly and log (see Logging) — don't add a blanket
  try/catch that discards the error.

## Async

- The entire SDK is synchronous (`HttpWebRequest`/`GetResponse()`, blocking).
  Don't introduce `async`/`await` into `LinnworksAPI/` inconsistently — if async
  support is ever added, it should be a deliberate, whole-SDK decision (new
  methods or a parallel async surface), not one-off per method.

## Logging

- Nothing in `LinnworksAPI/` logs on its own — it's a plain SDK, not a framework.
  Macro-level logging goes through `LinnworksMacroHelpers`/`LinnMacroCustomer`
  (`LoggerProxy.cs`, `Interfaces/ILogger.cs`), not through the SDK layer. Don't
  add `Console.WriteLine`/`Trace` calls inside `LinnworksAPI/` controllers.

## v1 vs v2

- v1 lives in the flat `LinnworksAPI` namespace; v2 lives in `LinnworksAPI.V2`.
  This is a hard rule, not a preference — v1 and v2 have already had a real name
  collision (`FulfillmentStatus` means different things in each), and mixing them
  in one namespace would silently resolve to whichever got compiled last.
- v1 calls are always `GetResponse(path, formEncodedBody, httpMethod)`. v2 calls
  are always `RestClient.Send<T>(apiContext, verb, path, query, body)` with a real
  JSON body and path-parameter substitution. Don't port v1 calling conventions
  into v2 code or vice versa - see `LinnworksAPI/V2/Controllers/Orders/OrdersController.cs`
  for the v2 shape.
- v2 code generated by `generate_v2_controller.py` may have **mechanically derived
  method names** where the spec had no `operationId` (see
  `WarehouseTransferController.cs`'s file header). Treat those as provisional, not
  as confirmed Linnworks naming, until checked against real usage.

## Golden examples

`references/standards/golden_examples/` has 3 real approved macros (supplied
2026-08-13), each annotated with what to copy and what to fix in
`golden_examples/README.md`. `macro_conventions.md` codifies the rules derived from
comparing them. Add more macros here as they're approved - re-derive/update the
rules in `macro_conventions.md` if a new example contradicts or extends them,
don't just accumulate examples without revisiting the rules.
